Solution Architect Field Guide

You are becoming the person who directs, evaluates, and approves AI-generated technical designs — not the person who hand-draws every box. This guide gives you the ~20% of solution architecture that makes that judgment possible, then shows you exactly what a complete, defensible architecture package looks like by building one, end to end, for a real (if invented) initiative.

How this guide works

Use the search box at the top to jump straight to a term, decision, or number. Use the Ask button in the bottom-right corner to ask a question in plain language — it answers from this guide's own content, entirely offline. Use the left navigation to browse by topic. Every one of the eight architecture documents can be downloaded individually as a standalone, fully-branded HTML file, printed to PDF, or — where the content is tabular — exported to CSV for Excel.

The guide has three parts:

  1. The Discipline — the concepts an architect needs to review, question, and approve AI-generated designs with authority: quality attributes, architecture styles, the C4 model, ADRs, trade-off analysis, patterns, fitness functions, build-vs-buy, and the review lens itself.
  2. The Example Initiative — one concrete, industry-grounded scenario (insurance claims), with requirements treated as already approved, so every document below has something real to say instead of generic placeholders.
  3. The Architecture Package — eight real, substantial, individually-downloadable documents: a Solution Architecture Document, C4 diagrams, Architecture Decision Records, an NFR specification, a technology trade-off matrix, sequence/data-flow diagrams, a risk register, and a one-page sign-off summary.
The mindset shift

An AI system can draft a plausible-looking architecture in seconds. Plausible is not the bar. Your job is to ask: does every number have a target, does every risky decision have a documented alternative that was rejected and why, and does the design admit its costs — not just its benefits? That is what the rest of this guide trains you to do.

Part One

Solution Architecture, Distilled

Solution architecture is not the same skill as software engineering, and it is not the same skill as enterprise architecture. It sits between business intent and engineering execution, and its entire value is making trade-offs explicit, measurable, and traceable before code gets expensive to change.

Why Solution Architecture Exists

Every non-trivial system embodies dozens of decisions that are expensive to reverse once built: which parts talk synchronously vs. asynchronously, where the system of record lives, how failures are contained, what gets logged for an audit three years from now. Left implicit, those decisions get made by default — by whichever engineer touched the code last, or by whichever AI tool generated the first draft. Solution architecture exists to make those decisions deliberately, visibly, and accountably, so that:

  • Engineering has a blueprint to build against instead of re-litigating structure in every pull request.
  • Leadership can govern cost, risk, and compliance exposure without reading source code.
  • The organization can explain, a year later, why a decision was made — to auditors, regulators, new hires, or itself.

The 20% You Must Know

You will not personally write the Kafka consumer group logic or tune the XGBoost hyperparameters. You need enough of the discipline to direct the work, spot a weak design, and defend an approval decision. That's this list — everything else in this guide teaches one of these nine things:

Quality attributes

The measurable "-ilities" that actually decide the architecture — not the feature list.

Architecture styles

Monolith, services, event-driven — each is correct for a different load and team shape.

The C4 model

One notation, four altitudes, so execs, architects, and engineers can look at the same system.

ADRs

A durable record of what was decided, what was rejected, and why — your main defense in an audit.

Trade-off analysis

Every decision buys one quality attribute at the expense of another. Name the price.

Key patterns

A short vocabulary (anti-corruption layer, strangler fig, circuit breaker, RAG, HITL) that covers most real designs.

Fitness functions

Automated checks that keep an architecture honest after launch, not just at design time.

Build vs. buy

A repeatable calculus, not a gut call, for when to use a vendor and when not to.

The review lens

The specific questions you ask before you approve anything — including an AI's first draft.

Quality Attributes (Non-Functional Requirements)

Functional requirements describe what a system does. Quality attributes describe how well it must do it — and they are what actually drive architecture. Two systems with identical features can require completely different architectures if one must serve 50 users and the other 50,000, or if one can tolerate a five-minute outage and the other cannot. The discipline is simple to state and easy to skip: every quality attribute needs a number, not an adjective. "Fast" is not a requirement; "p95 latency ≤ 3 seconds" is.

AttributeWhat it really meansTypical measurable target
Performance / LatencyHow quickly the system responds under normal loadp95 / p99 response time in milliseconds or seconds
Scalability / ThroughputHow volume is handled as it grows or spikesTransactions/day at steady state and at peak burst
AvailabilityHow much planned/unplanned downtime is tolerable99.9% monthly uptime (≈43 min/month)
SecurityProtection of data and access in transit and at restEncryption standard, access-control model, audit coverage
Compliance / AuditabilityRegulatory and legal obligations the system must prove it meetsNamed regulation + evidence artifact + review cadence
ExplainabilityWhether a decision (especially AI-made) can be justified to a human% of decisions with a retrievable reason code
MaintainabilityCost and speed of safely changing the system laterLead time to ship a defined class of change
Resilience / Fault toleranceBehavior when a dependency failsDefined degraded mode + recovery time objective
Cost efficiencyUnit economics of running the systemFully-loaded cost per transaction

Architecture Styles: Monolith vs. Services vs. Event-Driven

There is no universally "best" style — only the style that fits the load profile, team topology, and failure tolerance in front of you. An architect's job is to justify the choice against those three things, not against fashion.

StyleShapeFits whenWatch out for
Monolith (incl. modular monolith)Single deployable unit; internal module boundariesSmall team, low-to-moderate uniform load, early-stage product where speed of iteration beats independent scalingBecomes a single point of failure and a single scaling unit as load grows unevenly across features
Service-Oriented / MicroservicesIndependently deployable services, mostly synchronous callsMultiple teams need independent release cadence; components have genuinely different scaling needsNetwork calls replace function calls — latency, partial failure, and versioning all become real problems
Event-DrivenServices communicate through an event bus / stream, mostly asynchronousBursty or unpredictable load; multiple consumers need the same fact; natural buffering is valuableEventual consistency complicates UX; debugging a distributed trace is harder than reading a stack trace

The C4 Model

The C4 model (Context, Container, Component, Code) solves a communication problem: a single diagram can't serve a CFO and a backend engineer at the same time. Each level zooms in one step and is drawn for a different audience.

LevelShowsAudienceUsed in this guide?
1. ContextThe system as one box, its users, and the external systems it talks toExecutives, product, complianceYes — Document 2
2. ContainerThe deployable pieces inside the system (services, stores, apps) and how they connectArchitects, tech leadsYes — Document 2
3. ComponentThe internal structure of one containerEngineers building or reviewing that containerYes, for the Fraud Scoring Service — Document 2
4. CodeClasses / functions inside one componentThe engineer writing it, generated from the IDENo — changes too fast to be an architecture artifact; an architect reviews structure, not implementation
Review tip

If an AI-generated design skips straight to a Component diagram with no Context diagram, that's a red flag: it means the tool (or the engineer) started with the solution instead of the boundary. Ask for Context first, always.

Architecture Decision Records (ADRs)

An ADR is a short, permanent record of one significant, hard-to-reverse decision. Its value isn't the decision itself — it's the rejected alternatives and the reasoning, which is exactly the information that normally evaporates the moment a Slack thread scrolls away. A good ADR has five parts:

FieldPurpose
StatusProposed / Accepted / Superseded / Deprecated — decisions have a lifecycle
ContextThe forces at play: load, constraints, team, deadline, compliance
DecisionWhat was chosen, stated as a single clear sentence
Rejected optionsWhat else was seriously considered, and the specific reason each was rejected
ConsequencesWhat gets easier, what gets harder — both directions, always
Why architects insist on this

Three years from now, a regulator, a new CTO, or an incident review will ask "why did we build it this way?" An ADR answers that in thirty seconds. Its absence means someone has to reconstruct the reasoning from memory, or worse, guess. Six worked examples are in Document 3.

Trade-off Analysis

There is no option that wins on every criterion — if there were, it wouldn't be a decision. A trade-off analysis forces every option's costs onto the page next to its benefits, typically as a weighted scoring matrix: pick the criteria that matter (cost, latency, compliance fit, integration effort, lock-in risk...), weight them by importance, score each option, and let the arithmetic — not the loudest voice in the room — surface the leading candidate. The matrix doesn't make the decision for you; it makes the decision inspectable. Document 5 works four real ClaimSight decisions this way.

Key Patterns

PatternIn one line
Anti-Corruption LayerA translation boundary that keeps a legacy system's ugly data model from leaking into new code
Strangler FigMigrate a legacy system incrementally, routing one slice of traffic at a time to the new implementation
CQRSSeparate the model used to write data from the model used to read it, when their needs diverge sharply
Circuit BreakerStop calling a failing dependency for a cooldown period instead of piling up timeouts
SagaCoordinate a multi-step transaction across services with compensating actions instead of a distributed lock
API GatewayOne front door for client traffic that handles auth, rate limiting, and routing centrally
RAG (Retrieval-Augmented Generation)Ground an LLM's output in retrieved, trusted data instead of relying on its training memory alone
Human-in-the-Loop (HITL)A mandatory human checkpoint before a high-stakes AI-influenced decision takes effect

Fitness Functions

Borrowed from evolutionary biology via Neal Ford's Building Evolutionary Architectures: a fitness function is an automated, repeatable test that checks whether the architecture still meets an intended quality attribute — run continuously, not just at design review. It's what keeps an architecture honest after launch, when the pressure to cut corners is highest. Three concrete examples used on ClaimSight:

  • Latency fitness function — a synthetic transaction runs every 60 seconds against the Fraud Scoring Service; the build is blocked from promoting to production if p95 exceeds 3 seconds in staging soak tests.
  • Fairness fitness function — a monthly batch job computes the disparate impact ratio of the fraud model across state-protected classes; anything outside 0.8–1.25 pages the AI Governance Lead automatically.
  • Dependency fitness function — a CI step fails the build if a new open-source dependency introduces a license incompatible with Meridian's policy, or a known critical CVE.

Build vs. Buy

A repeatable calculus beats a gut call. Weigh:

  • Is it a differentiator or a commodity? Build what makes you competitively distinct; buy the rest.
  • Time to value — can a vendor get you live in weeks instead of months?
  • Total cost of ownership — not just license/API cost, but the operational burden of running it yourself.
  • Regulatory and data-residency fit — can a vendor even legally hold this data?
  • Exit cost — how hard is it to leave this vendor later?

ClaimSight's OCR and LLM decisions (ADR-003, and Decision A/B in the Trade-off Matrix) are worked build-vs-buy examples: both bought a commodity capability (document extraction, general-purpose language understanding) rather than building it, precisely because neither is Meridian's competitive differentiator — fast, explainable claims decisions are.

The Architect's Review Lens

This is the checklist you actually use. When an AI tool — or a vendor, or a junior engineer — hands you a proposed design, run it through these questions before you approve anything.

  1. Does every quality attribute have a number, not an adjective?
  2. Is the architecture style justified against actual load and team shape, not fashion or resume-building?
  3. Does a Context diagram exist, and does it match the stated list of integrations — nothing missing, nothing invented?
  4. Is there an ADR for every decision that would be expensive to reverse?
  5. Are rejected alternatives documented with real, specific reasons — not just "we chose X"?
  6. Does the trade-off analysis admit costs, not only the winning option's benefits?
  7. Is there a human-in-the-loop or override point wherever an AI component influences a high-stakes outcome?
  8. Are compliance and data-residency constraints addressed explicitly, not assumed?
  9. Is there a rollback or kill-switch for every AI-driven component?
  10. Are fitness functions defined to catch drift after launch, not just at design time?
  11. Is the total cost of ownership realistic at production volume — including inference/API costs, not just infrastructure?
Use it now

Every one of the eight documents below was built to pass this exact checklist. As you read them, try to break them — that's the review lens in action.

Part Two

Meridian Mutual Insurance & ClaimSight

Industry: Property & Casualty Insurance. The requirements below are treated as already reviewed and approved by the Claims VP, CISO, and Chief Actuary — this guide begins where the real work of a solution architect begins: turning approved requirements into an architecture someone can build, govern, and defend.

The Company

Meridian Mutual Insurance is a regional property & casualty carrier serving roughly 1.2 million policyholders across 38 states, writing auto, homeowners, and small-commercial lines. Claims operations run on a 40-year-old COBOL mainframe (system of record for the financial ledger and regulatory filings) fronted by a Guidewire PolicyCenter implementation for policy administration.

The Problem

First Notice of Loss (FNOL) intake is manual across web portal, mobile app, call center, and email/fax. Triage — deciding severity and routing a claim to the right adjuster — takes 2–3 days. Every claim is manually reviewed for fraud indicators by a Special Investigations Unit (SIU) that cannot keep pace with volume, and internal analysis estimates $18M/year in fraud leakage from inconsistent, backlog-driven review, plus adjuster time lost to data entry that AI-assisted extraction could eliminate.

The Initiative: ClaimSight

ClaimSight is an AI-augmented claims intake and fraud triage platform. It ingests FNOL submissions from every channel, extracts structured claim data from documents and photos, produces an explainable real-time fraud risk score, routes claims automatically for straight-through processing or adjuster review, and gives adjusters and SIU investigators a unified, AI-assisted case view — without becoming the system of record (the mainframe keeps that role through the rollout).

2.Business Context & Problem Statement

Meridian Mutual writes auto, homeowners, and small-commercial lines across 38 states for roughly 1.2 million policyholders. FNOL intake spans web portal, mobile app, call center, and email/fax, and triage currently takes 2–3 days because claim data must be manually keyed and manually assessed for severity. Every claim receives full manual SIU fraud review regardless of risk, which cannot scale with volume; internal analysis attributes approximately $18M/year in fraud leakage to inconsistent, backlog-driven review. ClaimSight is chartered to compress triage time, apply consistent explainable fraud scoring at intake, and free adjuster time from data entry — without disrupting policy administration (Guidewire PolicyCenter) or the mainframe's role as ledger of record.

3.Scope

In Scope

  • Multi-channel FNOL intake (portal, mobile, call center, email/PDF)
  • Document/image extraction (OCR + NLP)
  • Real-time explainable fraud risk scoring
  • Severity-based adjuster/SIU routing
  • Adjuster Workbench (unified AI-assisted case view)
  • Read/write integration with Guidewire PolicyCenter
  • Read/write integration with the legacy mainframe via an anti-corruption layer
  • Model governance, bias monitoring, and audit logging

Out of Scope (this phase)

  • Replacing the mainframe as system of record for the financial ledger
  • Automated claim payment issuance (remains a Guidewire/mainframe function)
  • Policy underwriting or pricing models
  • Litigation case management (handled by existing Legal systems)
  • Commercial lines above small-commercial (large/specialty commercial deferred)

4.Architecture Drivers

The architecture is shaped by five dominant forces, each traced to a measurable requirement in the Non-Functional Requirements Specification:

5.Architecture Style & Justification

ClaimSight is built as event-driven microservices: independently deployable services for intake, document processing, fraud scoring, and case management, communicating primarily through a managed Kafka event bus (Amazon MSK), with synchronous REST reserved for user-facing request/response traffic (portal, Adjuster Workbench). This was chosen over a modular monolith and over a purely synchronous services design; the full reasoning, load evidence, and rejected alternatives are recorded in ADR-001. In short: document processing and fraud scoring absorb the brunt of a CAT surge while case management and the portal do not, so independent scaling is required, and the event bus provides natural buffering that a synchronous design cannot.

6.Logical Architecture Overview

At the container level, ClaimSight comprises: a Web Portal and Mobile App for policyholder-submitted FNOL; an API Gateway as the single front door; a Claims Intake Service that validates and publishes intake events; a Document Processing Service that calls AWS Textract and Claude (via Bedrock) for extraction and summarization; a Fraud Scoring Service combining a rules engine, an XGBoost model, and SHAP-based explanation; a Case Management Service as the operational claims record; a Legacy Integration Adapter implementing the anti-corruption layer to Guidewire and the mainframe; an Adjuster Workbench web application; and shared platform services for notifications, model governance/audit logging, and a claims operational database (PostgreSQL, with pgvector for similar-claim retrieval). Full Context, Container, and Component diagrams are in Document 2; the runtime call sequence is in Document 6.

8.Integration Architecture

ClaimSight integrates with five categories of external system, all shown in the Context diagram (Document 2): Guidewire PolicyCenter (policy and coverage lookups, synchronous REST), the legacy claims mainframe (financial ledger and regulatory filings, nightly batch through the Legacy Integration Adapter), ISO ClaimSearch (industry claims-history and fraud-bureau lookups), a weather/CAT data provider (correlates claims with declared catastrophe events to pre-triage CAT surges), and the AWS AI services (Textract, Bedrock/Claude) consumed entirely within Meridian's AWS account boundary. No new external system becomes a system of record; ClaimSight is additive to, not a replacement of, Guidewire and the mainframe during this phase.

9.Data Architecture

The core operational entities are Claim, Policy Reference, Party (claimant/insured/witness), Document, Fraud Score, and Audit Event. Policy and coverage data is read from Guidewire, never duplicated as system of record; ClaimSight owns the claim-processing-state data and the AI-derived artifacts (extracted fields, fraud scores, explanations, embeddings).

Retention: active claim data is retained per the mainframe's regulatory schedule (typically 7 years post-close); AI audit artifacts (feature snapshots, model version, SHAP values) are retained 7 years to match NFR-EXPL-01. All claim documents and extracted PII are classified Restricted under Meridian's data classification policy and encrypted at rest (AES-256) and in transit (TLS 1.2+).

10.Security & Compliance Architecture

  • Identity & access — role-based access control; adjusters scoped to assigned states/lines; SIU investigators granted elevated read access with full audit trail.
  • Data protection — AES-256 at rest, TLS 1.2+ in transit, field-level tokenization for SSN/financial account numbers before any third-party AI service call.
  • Vendor governance — signed Data Processing Agreements with AWS (Textract, Bedrock) restricting sub-processing and prohibiting model training on Meridian customer data.
  • Data residency — all processing constrained to US AWS regions via Service Control Policies (NFR-COMP-01).
  • Compliance targets — SOC 2 Type II (platform), state DOI claims-handling regulations across 38 states, NAIC Model Bulletin on the Use of AI Systems by Insurers.
  • AI governance — see Section 11.

11.AI/ML Governance Model

Every AI-influenced outcome that could adversely affect a policyholder — a claim denial or an SIU fraud referral — requires a documented human decision before it takes effect (NFR-COMP-02). The Fraud Scoring Service logs a full feature snapshot, model version, and SHAP explanation for every score (NFR-EXPL-01), and a monthly automated fairness fitness function checks the model's disparate impact ratio across state-protected classes (NFR-FAIR-01), escalating to the AI Governance Lead on any breach of the 0.8–1.25 band. A model risk committee (Chief Actuary, CISO, AI Governance Lead) reviews model performance and fairness metrics quarterly and approves any model version promotion to production.

12.Deployment & Infrastructure

ClaimSight runs on AWS in a single primary US region across three Availability Zones, with a warm-standby DR region. Environments follow the standard progression (dev → staging → production) with staging soak-tested against the CAT-burst load profile before every production promotion. Services are containerized (ECS Fargate) with auto-scaling policies keyed to MSK consumer lag and API Gateway request rate, so the CAT-burst capacity target (NFR-SCALE-02) is met without manual intervention.

1.Purpose

This document provides the three C4 views an architect needs to review ClaimSight: Context (the system's boundary and its neighbors), Container (the deployable pieces inside that boundary), and Component (the internal structure of the highest-scrutiny container, the Fraud Scoring Service). 2.Level 1 — System Context

ClaimSight sits between four human actor groups and six external systems. It does not replace Guidewire or the mainframe; it orchestrates AI-assisted intake and triage around them.

3.Level 2 — Container View

Inside the ClaimSight boundary, eleven containers divide responsibility along the event-driven lines justified in ADR-001. The Event Bus (Amazon MSK) is the backbone: intake publishes claim-lifecycle events, and Document Processing, Fraud Scoring, Case Management, Notification, and Model Governance & Audit Log all consume from it independently.

4.Level 3 — Component View: Fraud Scoring Service

The Fraud Scoring Service receives the most regulatory and audit scrutiny of any container, so it is the one zoomed to component level. Every score passes through a deterministic rules check and the ML model, and every output — whether or not it triggers a human review — is written to the Audit Logger before the response returns (see ADR-004 for why XGBoost + SHAP was chosen over a black-box deep model).

Architecture Decision Records

ADR Log — Six Foundational Decisions

VersionStatusOwnerDateClassification
1.46 AcceptedDana Whitfield — Solution Architect, AI Platforms2026-07-07Internal — Architecture Governance

Six decisions govern ClaimSight's architecture. Each was expensive enough to reverse that it warranted a formal record — the format used throughout is Status / Context / Decision / Rejected Options / Consequences, per the "Architecture Decision Records" section of the Discipline chapter.

ADR-001 · Event-Driven Microservices over a Modular Monolith

Accepted · 2026-06-02
Context

Claims intake, document processing, fraud scoring, and case management have different scaling profiles — CAT bursts hit intake and document processing hardest — and different release cadences (fraud model updates monthly vs. case UI weekly). The platform must integrate with a legacy mainframe and Guidewire without becoming coupled to either's release cycle.

Decision

Decompose into independently deployable services (Claims Intake, Document Processing, Fraud Scoring, Case Management, Legacy Adapter) communicating primarily through an event bus, with synchronous REST reserved for user-facing request/response traffic.

Rejected Options
Modular monolith. Rejected — cannot scale document processing or fraud scoring independently during a CAT burst without over-provisioning the entire application; a single deploy unit raises blast radius for frequent ML model updates.
Full microservices, synchronous REST-only. Rejected — tight coupling and cascading-failure risk under CAT-burst load, with no natural buffering for a 12x volume spike.
Consequences

+ Independent scaling and deployment; natural burst buffering via the event bus. − Higher operational complexity (distributed tracing, eventual consistency); the team must design for idempotency and out-of-order events.

Compliance / Risk Notes

Raises the profile of RISK-12 (event-bus single point of failure), mitigated by a multi-AZ MSK deployment — see the Risk Register.

ADR-002 · Anti-Corruption Layer + Strangler Fig for Legacy Mainframe Integration

Accepted · 2026-06-09
Context

The legacy COBOL claims mainframe remains system of record for the financial ledger and regulatory filings throughout the 14-month rollout. A big-bang replacement is not viable given regulatory filing dependencies and a 40-year-old, largely undocumented codebase.

Decision

Build a Legacy Integration Adapter service implementing the Anti-Corruption Layer pattern to translate ClaimSight's domain model to and from the mainframe's batch format and Guidewire's API. New claim types are incrementally "strangled" from batch processing to real-time processing, state by state.

Rejected Options
Direct mainframe integration from every service. Rejected — propagates a 1980s data model (fixed-width fields, magic numbers) throughout the new codebase and makes future mainframe retirement harder.
Big-bang mainframe replacement before launch. Rejected — an 18–24 month critical-path dependency the business cannot absorb, with unacceptable regulatory filing risk.
Consequences

+ Core services stay clean and testable; the mainframe can be retired later without touching them. − The adapter becomes a critical dependency requiring its own resilience investment; the 4-hour nightly batch window remains a temporary throughput constraint (RISK-03).

ADR-003 · Anthropic Claude via AWS Bedrock for Document Understanding & Narrative Generation

Accepted · 2026-06-16
Context

ClaimSight must summarize free-text loss descriptions, extract structured facts from police/medical reports, and draft adjuster-facing claim narratives — within Meridian's existing AWS footprint and under strict data-governance terms (no vendor training on customer data, US data residency, SOC 2 Type II sub-processor).

Decision

Use Anthropic Claude models via AWS Bedrock as the managed LLM provider, orchestrated by the Document Processing Service, with every prompt and output logged for audit (NFR-EXPL-01).

Rejected Options
OpenAI GPT via Azure OpenAI. Rejected — introduces a second cloud provider and a new compliance/security review cycle for marginal quality gain; see Decision B in the Trade-off Matrix.
Self-hosted open-weight model (Llama-class). Rejected at this stage — requires building net-new MLOps/GPU operating capability the team does not yet have (RISK-08). Revisit if per-claim LLM cost trends above the NFR-COST-01 threshold.
Consequences

+ Fast integration inside the existing AWS/Bedrock security boundary; contractual no-train guarantee simplifies compliance review. − Ongoing per-token cost exposure (RISK-07); single-vendor LLM dependency, mitigated by the rules-engine fallback in ADR-004 and NFR-AVAIL-02.

ADR-004 · Gradient-Boosted Trees (XGBoost) + SHAP over a Deep Neural Network for Fraud Scoring

Accepted · 2026-06-23
Context

The fraud score must be explainable to SIU investigators and defensible in DOI inquiries and litigation (NFR-EXPL-01, NFR-COMP-02), and must train on Meridian's structured claims history (~40 tabular features) without a large unstructured training corpus.

Decision

Use an XGBoost gradient-boosted tree model for the core fraud risk score, paired with SHAP to generate per-claim reason codes, supplemented by a deterministic red-flag rules engine for known fraud indicators (e.g., a claim filed within 48 hours of policy inception).

Rejected Options
Deep neural network (tabular). Rejected — a +1.2 AUC point gain in internal benchmarking did not justify materially weaker explainability and higher retraining/operations cost; explainability is a hard regulatory requirement here, not a nice-to-have.
Rules engine only, no ML. Rejected — cannot adapt to evolving fraud patterns; caught only ~35% of confirmed fraud in retrospective analysis.
Consequences

+ Every score ships with human-readable top-5 reason codes; faster training cycle supports monthly refresh. − A ceiling on achievable accuracy relative to deep-learning approaches — revisit if fraud typology shifts toward unstructured signal (e.g., image forensics) as the primary driver.

ADR-005 · Amazon MSK (Managed Kafka) as the Claims Event Backbone

Accepted · 2026-06-30
Context

Claims intake, document processing, fraud scoring, and case management must communicate asynchronously with per-claim ordering guarantees, replay capability for downstream recovery, and the ability to absorb 12x volume bursts during CAT events (ADR-001).

Decision

Adopt Amazon MSK as the event backbone. Each claim's lifecycle events publish to claim-partitioned Kafka topics (partition key = claim ID), ensuring per-claim ordering; downstream services consume independently and can replay from offset on recovery.

Rejected Options
Amazon SQS / SNS. Rejected — standard queues don't guarantee ordering at throughput, FIFO queues cap at 3,000 msg/sec per queue (insufficient for a CAT burst), and neither supports replay.
Azure Service Bus. Rejected — introduces a second cloud provider for a capability AWS already provides natively, adding integration and compliance overhead for no functional gain; see Decision C in the Trade-off Matrix.
Consequences

+ Ordered, replayable event stream supports both real-time and reprocessing use cases; scales to CAT bursts. − The team must build Kafka consumer-group operating expertise (RISK-08), partially offset by MSK being managed; eventual consistency requires careful UX design in the Adjuster Workbench (e.g., "processing" states).

ADR-006 · pgvector on Existing Postgres for Similar-Claim Retrieval (RAG)

Accepted · 2026-07-07
Context

SIU investigators and the fraud model benefit from retrieving similar historical claims — semantic similarity on loss narrative plus structured features — to ground fraud scoring and investigation with precedent. Claims data already lives in an operational Postgres database and must stay within Meridian's existing security boundary.

Decision

Use the pgvector extension on the existing Claims Operational Database to store narrative embeddings and perform similarity search, rather than introducing a separate vector database product.

Rejected Options
Amazon OpenSearch k-NN. Rejected — adds a second data store to keep synchronized with the system of record, and additional operational surface, for a marginal latency benefit at current data volumes.
Standalone managed vector DB (e.g., Pinecone). Rejected — a third-party SaaS holding derived claims data would require a new data processing agreement and re-opens data-residency review for no capability the existing database can't provide at this scale; see Decision D in the Trade-off Matrix.
Consequences

+ No new data store to operate or secure; similarity search participates in existing transactions and backup/DR. − pgvector's approximate-nearest-neighbor performance should be re-evaluated if claim history grows beyond ~50 million embedded narratives — revisit this decision at that threshold.

1.Method

Four technology decisions were scored with a weighted matrix: criteria relevant to that decision are weighted to sum to 100%, each option is scored 1–5 per criterion (5 = best; lock-in/ops-overhead criteria are scored so that 5 = lowest risk), and the weighted total surfaces the leading candidate. The matrix does not remove judgment — it makes the judgment inspectable. Every selected option also has a full ADR with rejected-option reasoning; this document shows the arithmetic behind it.

Glossary

NFR
Non-Functional Requirement — a measurable quality attribute target (e.g., latency, availability).
ADR
Architecture Decision Record — a documented, hard-to-reverse decision with rejected alternatives.
C4
Context, Container, Component, Code — a four-level architecture diagramming model.
FNOL
First Notice of Loss — the initial claim report from a policyholder.
STP
Straight-Through Processing — a claim handled end-to-end without manual adjuster intervention.
SIU
Special Investigations Unit — the team that investigates suspected insurance fraud.
Anti-Corruption Layer
A translation boundary isolating new code from a legacy system's data model.
Strangler Fig
Incremental legacy migration pattern — route traffic to the new system one slice at a time.
RAG
Retrieval-Augmented Generation — grounding an LLM's output in retrieved, trusted data.
LLM
Large Language Model — used here for document summarization and narrative drafting.
Vector Database
A data store optimized for similarity search over embeddings (e.g., pgvector).
SHAP
SHapley Additive exPlanations — a method for explaining individual ML model predictions.
XGBoost
A gradient-boosted decision tree algorithm, chosen here for explainable fraud scoring.
MSK
Amazon Managed Streaming for Apache Kafka — the managed event backbone.
CQRS
Command Query Responsibility Segregation — separating write and read models.
Circuit Breaker
A pattern that stops calling a failing dependency for a cooldown period.
Fitness Function
An automated, repeatable test that continuously validates a quality attribute.
TCO
Total Cost of Ownership — full cost of a solution including operations, not just license/API fees.
SLA / SLO / SLI
Service Level Agreement / Objective / Indicator — the contract, target, and measurement of a service's reliability.
PII
Personally Identifiable Information — data requiring special handling and access controls.
SOC 2 Type II
An audit standard evaluating a service organization's controls over an extended period.
NAIC
National Association of Insurance Commissioners — issues model regulations adopted by states, including AI governance.
HITL
Human-in-the-Loop — a mandatory human checkpoint before a high-stakes automated decision takes effect.
API Gateway
A single front door for client traffic handling authentication, rate limiting, and routing.
Idempotency
A property where repeating the same operation produces the same result — critical for safe event retries.
CAT Event
Catastrophe event (e.g., hurricane, hailstorm) causing an extreme, short-term claims volume surge.
